第 8 章　内存一致性模型（Memory Consistency Model）

在多线程执行中，每个线程所执行的内存操作的"副作用"（side-effect），对其他线程而言是以一种局部且各不相同的顺序变得可见的。这意味着：任意两个操作，在不同线程看来，可能表现为"没有顺序关系"，也可能表现为"不同的先后顺序"。由memory consistency model（内存一致性模型）所引入的一系列公理，精确规定了不同线程观察到的操作顺序之间，哪些矛盾是被禁止的。

在没有任何约束的情况下，每个读操作都会返回"某个对同一个内存位置执行过写操作并提交的值"——包括对该内存位置的初始写。内存一致性模型实质上约束了"读操作可以从中取值的候选写操作集合"。

为什么 GPU 要用weak/relaxed memory model（弱内存模型）？　GPU 拥有成千上万个并发线程，硬件为了吞吐量与延迟隐藏，会积极地重排、缓冲、延迟内存访问的全局可见性。若强制顺序一致（sequential consistency），会严重拖慢执行。因此 PTX 采用weak/relaxed memory model（弱内存模型）：默认情况下线程间不保证写操作的立即可见与顺序，只有显式使用fence / membar（内存屏障）（如 fence / membar）或带序修饰符（.release / .acquire）的指令，才建立跨线程的同步关系。这也正是 CUDA C++ 中 __threadfence() / __threadfence_block() 的底层语义来源。

8.1　模型的作用域与适用条件（Scope and applicability of the model）

本模型所规定的约束，适用于任意 PTX ISA 版本号、运行在 sm_70 或更高架构上的 PTX 程序。

该内存一致性模型不适用于纹理（包括 ld.global.nc）与表面（surface）访问。

8.1.1　系统作用域下原子性的限制（Limitations on atomicity at system scope）

当与主机 CPU 通信时，某些系统作用域（system scope）的强操作（strong operation）在某些系统上可能无法以原子方式执行。关于对主机内存原子性保证的更多细节，请参见 CUDA Atomicity Requirements。

8.2　内存操作（Memory operations）

PTX 内存模型中的基本存储单元是一个字节（byte），由 8 位组成。PTX 程序可用的每个状态空间（state space）都是内存中一段连续的字节序列。PTX 状态空间中的每个字节，对所有能够访问该状态空间的线程而言，都拥有唯一地址。

每条 PTX 内存指令都指定一个地址操作数和一个数据类型。地址操作数包含一个虚拟地址（virtual address），在内存访问过程中被转换为物理地址（physical address）。物理地址与数据类型的大小共同定义了一个物理内存位置（physical memory location）——即从物理地址开始、长度延伸至数据类型字节大小的一段字节范围。类似地，地址操作数与数据类型大小共同定义了该内存操作所访问的虚拟内存地址范围。

内存一致性模型的规范中，术语"地址"（address / memory address）指虚拟地址，术语"内存位置"（memory location）指物理内存位置。

每条 PTX 内存指令还指定了要在对应内存位置的所有字节上执行的操作——读（read）、写（write）或原子读-改-写（atomic read-modify-write）。

8.2.1　重叠（Overlap）

当两个内存位置中，其中一个的起始地址落在另一个位置所占的字节范围内时，称这两个内存位置"重叠"。当两个内存操作所访问的虚拟地址范围相交时，称这两个内存操作"重叠"。若两个内存位置完全相同，则称重叠为"完全重叠"（complete）；否则为"部分重叠"（partial）。

8.2.2　别名（Aliases）

若两个不同的虚拟地址映射到同一个内存位置，则称它们互为"别名"（aliases）。

8.2.3　多内存地址（Multimem Addresses）

多内存地址（multimem address）是一个指向跨设备多个不同内存位置的虚拟地址。

只有在 multimem 地址上执行 multimem.* 操作才是合法的。换言之，在任何其他内存操作中访问 multimem 地址，其行为是未定义的（undefined）。

8.2.4　向量数据类型上的内存操作（Memory Operations on Vector Data Types）

内存一致性模型将"在标量数据类型（最大尺寸与对齐均为 64 位）的内存位置上执行的操作"关联起来。向量数据类型的内存操作被建模为一组等价的标量数据类型内存操作，按未指定顺序作用于向量中的各个元素。

8.2.5　打包数据类型上的内存操作（Memory Operations on Packed Data Types）

打包数据类型（packed data type）由两个相同标量数据类型的值组成（见 Packed Data Types 一节）。这些值被存放在相邻的内存位置中。对打包数据类型的内存操作被建模为一对等价的标量数据类型内存操作，按未指定顺序作用于打包数据的每个元素。

8.2.6　初始化（Initialization）

内存中的每个字节，都由程序启动任何线程之前执行的一个假想写操作 W0 完成初始化。若该字节属于某个程序变量，且该变量有初值，则 W0 向该字节写入对应的初值；否则假定 W0 向该字节写入了一个未知但恒定的值。

8.3　状态空间（State spaces）

内存一致性模型中定义的关系与状态空间无关。特别是，因果序（causality order）覆盖所有状态空间上的全部内存操作。但是，某个状态空间中的内存操作的副作用，只能被同样能够访问该状态空间的操作直接观察到。除作用域（scope）之外，这进一步约束了内存操作的同步效果。例如，PTX 指令 ld.relaxed.shared.sys 的同步效果与 ld.relaxed.shared.cluster 完全相同，因为同一 cluster 之外的线程无法执行访问同一内存位置的操作。

8.4.1　mmio 操作

mmio 操作是指定 .mmio 修饰符的内存操作。它通常作用于映射到对端 I/O 设备控制寄存器的内存位置。它也可用于线程间通信，但相对于非 mmio 操作性能较差。

mmio 操作的语义含义无法被精确定义，因为它由底层的 I/O 设备决定。从内存一致性模型的角度出发，mmio 操作的语义形式化等价于一个强操作的语义。但在满足指定作用域下 CUDA 原子性要求的前提下，它遵循若干实现相关的特性：

  • 写操作总是被执行，且在指定作用域内不会被合并（combined）。
  • 读操作总是被执行，且不会被转发（forwarded）、预取（prefetched）、合并（combined），也不允许命中指定作用域内的任何缓存。
  • 作为例外：在某些实现中，可能同时加载其周边位置。这种情况下加载的数据量是实现相关的，大小在 32 到 128 字节之间浮动。

8.4.2　volatile 操作

volatile 操作是指定 .volatile 修饰符的内存操作。volatile 操作的语义等价于"系统作用域下 relaxed 的内存操作"，但带有以下额外的实现相关约束：

  • 程序所执行的 volatile 指令（注意是"指令"而非"操作"）的数量被保留。硬件可能合并由多个不同 volatile 指令发出的 volatile 操作——也就是说，程序中 volatile 操作的数量不被保留。
  • volatile 指令不会绕到其他 volatile 指令周围重排，但这些指令所执行的内存操作之间可能被相互重排。
注意　PTX 的 volatile 操作旨在供编译器将来自 CUDA C++（以及共享 CUDA C++ volatile 语义的其他编程语言）的 volatile 读写 lowering 为 PTX。由于 volatile 操作本质上是系统作用域下带额外约束的 relaxed 操作，建议在线程间同步时改用其他强读 / 强写操作（例如 ld.relaxed.sys 或 st.relaxed.sys），可能获得更好性能。PTX volatile 操作不适合用于内存映射 I/O（MMIO），因为它不保留所执行内存操作的数量，可能以非确定方式执行多于或少于请求的操作次数。请改用 .mmio 操作，它会严格保留所执行操作的数量。

8.6　代理（Proxies）

内存代理（memory proxy，简称 proxy）是一个应用于某种内存访问方法的抽象标签。当两个内存操作使用不同的内存访问方法时，称它们是不同的代理（proxy）。

跨不同代理同步内存操作需要一个代理屏障（proxy fence）。尽管虚拟别名（virtual alias）使用通用的内存访问方法，但由于使用不同的虚拟地址表现得"如同使用不同代理"，因此它们需要一个代理屏障来建立内存顺序。

除非另有说明，操作类型（Operation types）一节中定义的内存操作使用通用的内存访问方法，即通用代理（generic proxy）。使用区别于通用方法的访问方法的操作包括：

  • 纹理与表面访问；
  • 通过同一代理、使用不同虚拟内存地址访问同一位置；
  • .async.bulk 操作带来的 async-proxy 与 tensormap-proxy 访问；
  • fabric 操作带来的 fabric-proxy 访问。

8.6.1　强代理访问（Strong Proxy Accesses）

通过以下代理的强修改（strong modification）：

  • generic-proxy（通用代理），
  • async-proxy，
  • tensormap-proxy，
  • fabric-proxy，

最终能够通过该列表中"不同代理"对同一位置执行的强访问观察到，前提是修改与访问满足：

  • 系统作用域（system-scope）——即使它们使用了不同的内存地址；或
  • GPU 作用域（gpu-scope），且所涉及的代理属于下列列表： async-proxy、generic-proxy。

8.7　道德强操作（Morally strong operations）

当两个操作满足以下所有条件时，称它们彼此"道德强"（morally strong）：

  • 这两个操作在程序序（program order）上相关（即都由同一线程执行）；或者每个操作都是强操作，且指定的作用域包含执行另一操作的线程。
  • 两个操作都通过同一代理执行。
  • 若两者都是内存操作，则它们完全重叠（overlap completely）。

内存一致性模型中的大多数（但不是全部）公理，都依赖于道德强操作之间的关系。

8.7.1　冲突与数据竞争（Conflict and Data-races）

当两个重叠的内存操作中至少有一个是写操作时，称它们"冲突"（conflict）。

当两个冲突的内存操作既不在因果序（causality order）上相关，也不是道德强（morally strong）时，称它们处于"数据竞争"（data-race）之中。

8.7.2　混合尺寸数据竞争的限制（Limitations on Mixed-size Data-races）

完全重叠操作之间的数据竞争称为"同尺寸数据竞争"（uniform-size data-race），而部分重叠操作之间的数据竞争称为"混合尺寸数据竞争"（mixed-size data-race）。

如果某 PTX 程序包含一个或多个混合尺寸数据竞争，内存一致性模型中的公理将不再适用。但这些公理足以描述"仅含同尺寸数据竞争"的 PTX 程序的行为。

混合尺寸 RMW 操作的原子性（Atomicity of mixed-size RMW operations）

在任何含或不含混合尺寸数据竞争的程序中，对每一对重叠的原子操作 A1 与 A2（且各自指定的作用域包含对方），以下性质成立：要么 A1 所规定的读-改-写操作在 A2 启动之前完整执行，要么反之。无论 A1 与 A2 是部分重叠还是完全重叠，该性质均成立。

8.8　释放与获取模式（Release and Acquire Patterns）

某些指令序列会产生参与内存同步的模式（详见后文）。释放（release）模式使当前线程此前的操作1对其他线程的某些操作可见。获取（acquire）模式使其他线程的某些操作对当前线程此后的操作可见。release/acquire（释放/获取语义）是这类模式的核心。

位于位置 M 上的一个释放模式，由以下之一组成：

  • 在 M 上的一个释放操作。例如：st.release [M]; 或 atom.release [M]; 或 mbarrier.arrive.release [M];
  • 或在程序序上，一个释放 / 获取-释放操作后跟一个对 M 的强写。例如：st.release [M]; st.relaxed [M];
  • 或在程序序上，一个释放 / 获取-释放的内存屏障后跟一个对 M 的强写。例如：fence.release; st.relaxed [M]; 或 fence.release; atom.relaxed [M];
  • 或在程序序上，一个释放 / 获取-释放的内存屏障后跟一个对 M 执行强写的异步操作。例如：fence.release; cp.async.bulk.global.shared.relaxed.sys.b128 [M];
  • 或一个对 M 执行强写的释放异步操作。例如：st.async.release.sys [M];

释放模式所建立的任何内存同步，仅影响该模式第一条指令之前、程序序上的操作。

位于位置 M 上的一个获取模式，由以下之一组成：

  • 在 M 上的一个获取操作。例如：ld.acquire [M]; 或 atom.acquire [M]; 或 mbarrier.test_wait.acquire [M];
  • 或在程序序上，一个对 M 的强读后跟一个对 M 的获取操作。例如：ld.relaxed [M]; ld.acquire [M];
  • 或在程序序上，一个对 M 的强读后跟一个获取内存屏障。例如：ld.relaxed [M]; fence.acquire; 或 atom.relaxed [M]; fence.acquire;
  • 或先观察到某个对 M 执行强读的异步操作的完成，然后该观察在程序序上后跟一个获取内存屏障。例如：
cp.async.bulk.mbarrier::complete_tx::bytes.relaxed.sys.b128 [dst], [M], size, [barrier]; // 对 M 的强读
mbarrier.try_wait.relaxed p, [barrier];  // 观察到执行对 M 强读的异步操作完成
@p fence.acquire; // 在观察到完成之后、程序序上的获取屏障

获取模式所建立的任何内存同步，仅影响该模式最后一条指令之后、程序序上的操作。

注意　虽然原子归约（atomic reduction）在概念上作为其读-改-写序列的一部分执行了一次强读，但这条强读并不构成获取模式。例如：red.add [M], 1; fence.acquire; 不是一个获取模式。

1 对于释放与获取模式，该效果通过因果序的传递性进一步扩展到其他线程的操作。

8.9　内存操作的排序（Ordering of memory operations）

每个线程执行的操作序列被记录为程序序（program order），而跨线程的内存同步被记录为因果序（causality order）。内存操作副作用对其他内存操作的可见性被记录为通信序（communication order）。内存一致性模型定义了"通信序"与"因果序和程序序"之间所禁止的矛盾。

8.9.1　程序序（Program Order）

程序序将一个线程执行的所有操作，关联到对应 PTX 源码中顺序处理器执行指令的次序。它是一个传递关系，在该线程所执行的操作上构成全序（total order），但不关联来自不同线程的操作。

8.9.1.1　异步操作（Asynchronous Operations）

某些 PTX 指令（cp.async、cp.async.bulk、cp.reduce.async.bulk、wgmma.mma_async 的所有变体）执行相对于执行该指令的线程而言是异步的操作。这些异步操作被排在"同一线程中先前指令"之后（wgmma.mma_async 除外），但它们不属于该线程程序序的一部分。相反，它们提供指令描述中所记载的更弱的排序保证。

例如，作为 cp.async 一部分执行的加载与存储彼此之间是有序的，但不与同一线程发起的任何其他 cp.async 指令有序，也不与该线程随后发出的任何其他指令有序——除非是 cp.async.commit_group 或 cp.async.mbarrier.arrive。由 cp.async.mbarrier.arrive 指令执行的异步 mbarrier arrive-on 操作，与同一线程发起的所有先前 cp.async 操作所执行的内存操作有序，但不与该线程发出的任何其他指令有序。cp.async.bulk 与 cp.reduce.async.bulk 所有变体所隐含的 mbarrier complete-tx 操作，仅与同一异步指令所执行的内存操作有序，特别地，它不会传递式地对该发起线程的先前指令建立顺序。

8.9.2　观察序（Observation Order）

观察序（observation order）通过一个可选的原子读-改-写操作序列，将一个写 W 与一个读 R 关联起来。

当满足以下条件时，称写 W 在观察序上先于读 R：

  • R 与 W 道德强（morally strong），且 R 读取了 W 所写入的值；或
  • 存在某原子操作 Z，使得 W 在观察序上先于 Z，且 Z 在观察序上先于 R。

8.9.3　Fence-SC 序（Fence-SC Order）

Fence-SC 序是一个在运行时确定的、无环的偏序（acyclic partial order），它关联每一对道德强的 fence.sc 操作。

8.9.4　内存同步（Memory synchronization）

不同线程执行的同步操作在运行时按此处描述的方式彼此同步。这种同步的效果是在线程间建立因果序。

  • 若 fence.sc 操作 X 在 Fence-SC 序上先于 fence.sc 操作 Y，则 X 与 Y 同步。
  • bar{.cta}.sync 或 bar{.cta}.red 或 bar{.cta}.arrive 操作，与在同一屏障上执行的 bar{.cta}.sync 或 bar{.cta}.red 操作同步。
  • barrier.cluster.arrive 操作与 barrier.cluster.wait 操作同步。
  • 若释放模式 X 中的某个写操作在观察序上先于获取模式 Y 中的某个读操作，且 X 的第一条操作与 Y 的最后一条操作道德强，则释放模式 X 与获取模式 Y 同步。

API 同步（API synchronization）

"同步"（synchronizes）关系也可由某些 CUDA API 建立。

  • 在 CUDA 流（stream）中入队（enqueue）的任务完成时，与该流中随后的任务开始同步（若有）。
  • 为此，在流中记录（record）或等待（wait）一个 CUDA 事件，或因 cudaStreamLegacy 导致插入跨流屏障，都会在该关联流中入队任务，即使没有直接副作用。事件记录任务与匹配的事件等待任务同步，屏障到达任务与匹配的屏障等待任务同步。
  • CUDA kernel 的开始与 kernel 中所有线程的开始同步。kernel 中所有线程的结束与 kernel 的结束同步。
  • CUDA 图的开始与图中所有源节点的开始同步。CUDA 图中所有汇节点（sink node）的完成与图的完成同步。图节点的完成与所有直接依赖节点的开始同步。
  • 入队任务的 CUDA API 调用的开始与该任务的开始同步。
  • 写入流的最后一个任务（若有）的完成与 cudaStreamSynchronize 的返回同步。最近入队的匹配事件记录任务（若有）的完成与 cudaEventSynchronize 的返回同步。同步一个 CUDA 设备或上下文，表现得如同同步该上下文中所有流（包括已销毁的流）。
  • 从查询 CUDA 句柄（如流或事件）的 API 返回 cudaSuccess，行为与从匹配的同步 API 返回相同。

除建立同步关系外，上述 CUDA API 同步机制还参与"代理保留的基因果序"（proxy-preserved base causality order），但 tensormap-proxy 例外——它在 CUDA kernel 开始时并未从 generic-proxy 获取，因此需要在需要时显式用 fence.proxy.tensormap::generic.acquire 获取。

8.9.5　因果序（Causality Order）

因果序刻画了内存操作如何通过同步操作跨线程变得可见。公理"Causality"利用该顺序约束读操作可从中读取值的写操作集合。

因果序中的关系主要由"基因果序"1（base causality order）中的关系构成，基因果序是一个在运行时确定的传递序。

基因果序（Base causality order）

当满足以下条件时，称操作 X 在基因果序上先于操作 Y：

  • X 在程序序上先于 Y；或
  • X 与 Y 同步（synchronizes with）；或
  • 存在某操作 Z：
  • X 在程序序上先于 Z，且 Z 在基因果序上先于 Y；或
  • X 在基因果序上先于 Z，且 Z 在程序序上先于 Y；或
  • X 在基因果序上先于 Z，且 Z 在基因果序上先于 Y。

代理保留的基因果序（Proxy-preserved base causality order）

当 X 在基因果序上先于 Y，且满足以下条件时，称内存操作 X 在代理保留的基因果序上先于内存操作 Y：

  • X 与 Y 使用通用代理（generic proxy）作用于同一地址；或
  • X 与 Y 使用同一代理、由同一线程块作用于同一地址；或
  • X 与 Y 互为别名，且从 X 到 Y 的基因果路径上存在一个别名代理屏障（alias proxy fence）。

因果序（Causality order）

因果序将基因果序与某些非传递关系组合如下：

当满足以下条件时，称操作 X 在因果序上先于操作 Y：

  • X 在代理保留的基因果序上先于 Y；或
  • 存在某操作 Z，X 在观察序上先于 Z，且 Z 在代理保留的基因果序上先于 Y。

1 基因果序的传递性体现了同步操作的"累积性"（cumulativity）。

8.9.6　相干序（Coherence Order）

存在一个在运行时确定的、传递的偏序，称为相干序（coherence order）1，它关联重叠的写操作。两个重叠的写操作，若它们道德强或在因果序上相关，则在相干序上相关。两个重叠的写若处于数据竞争中，则在相干序上无关——这正是相干序呈"偏序"的原因。

1 相干序无法被直接观察，因为它完全由写操作构成。它只能通过"约束读操作可从中读取的候选写集合"这一用途被间接观察。

8.9.7　通信序（Communication Order）

通信序是一个在运行时确定的、非传递的序，它关联写操作与其他重叠的内存操作。

  • 若读 R 返回了 W 所写入的任意字节的值，则写 W 在通信序上先于重叠的读 R。
  • 若 W 在相干序上先于写 W′，则写 W 在通信序上先于写 W′。
  • 若对于 R 与 W 共同访问的任意字节，R 返回了"在相干序上先于 W 的写 W′"所写入的值，则读 R 在通信序上先于重叠的写 W。

通信序刻画了内存操作的可见性——当内存操作 X1 在通信序上先于内存操作 X2 时，称 X1 对 X2"可见"（visible）。

8.10　公理（Axioms）

8.10.1　相干（Coherence）

若写 W 在因果序上先于重叠的写 W′，则 W 必须在相干序上先于 W′。

8.10.2　Fence-SC

Fence-SC 序不能与因果序矛盾。对于一对道德强的 fence.sc 操作 F1 与 F2，若 F1 在因果序上先于 F2，则 F1 必须在 Fence-SC 序上先于 F2。

8.10.3　原子性（Atomicity）

单副本原子性（Single-Copy Atomicity）

冲突的道德强操作用单副本原子性（single-copy atomicity）执行。当读 R 与写 W 道德强时，对于 R 与 W 共同访问的字节集合，同一次执行中不能同时存在以下两种通信：

  • R 从 W 读取任意字节。
  • R 从任意"在相干序上先于 W 的写 W′"读取任意字节。

读-改-写（RMW）操作的原子性（Atomicity of read-modify-write operations）

当原子操作 A 与写 W 重叠且道德强时，对于 A 与 W 共同访问的字节集合，同一次执行中不能同时存在以下两种通信：

  • A 从"在相干序上先于 W 的写 W′"读取任意字节。
  • A 在相干序上跟随 W。

Litmus Test 1（公理性测试 1）

Litmus Test 1
T1T2
 
.global .u32 x = 0;

A1: atom.sys.inc.u32 %r0, [x];
 
A2: atom.sys.inc.u32 %r0, [x];
最终状态（FINAL STATE）：x == 2

当操作道德强时，原子性得到保证。

Litmus Test 2（公理性测试 2）

Litmus Test 2
T1T2（位于不同 CTA）
 
.global .u32 x = 0;

A1: atom.cta.inc.u32 %r0, [x];
 
A2: atom.gpu.inc.u32 %r0, [x];
最终状态（FINAL STATE）：x == 1 或 x == 2

若操作不是道德强，则原子性不被保证。

8.10.4　无中生有（No Thin Air）

值不得"无中生有"（out of thin air）：一次执行不能投机地产生某个值，从而通过指令依赖链与线程间通信使该投机自我满足。这与程序员的直觉和硬件现实一致，但在做形式化分析时有必要显式说明。

Litmus Test：带真实依赖的加载缓冲（Load Buffering with true dependencies）

Litmus Test: LB+deps
T1T2
 
.global .u32 x = 0;
.global .u32 y = 0;

A1: ld.global.u32 %r0, [x];
B1: st.global.u32 [y], %r0;
 
A2: ld.global.u32 %r1, [y];
B2: st.global.u32 [x], %r1;
最终状态（FINAL STATE）：x == 0 且 y == 0

名为"LB+deps"（带依赖的加载缓冲）的 litmus test，检验了这种可能"无中生有"的被禁值。线程 T1 与 T2 各自从第一个变量读取值，并将观察到的结果复制到第二个变量中，两个变量在线程间互换。若每个变量初值均为 0，则最终结果也应为 0。若 A1 读取自 B2、且 A2 读取自 B1，则经由本例内存操作传递的值构成一个环：A1→B1→A2→B2→A1。只有 x == 0 与 y == 0 这两种值被允许满足该环。若本例中任一内存操作投机式地给对应内存位置关联了不同的值，那么该投机将自我实现，因此被禁止。

Litmus Test：无依赖的加载缓冲（Load Buffering without dependencies）

Litmus Test: LB (no deps)
T1T2
 
.global .u32 x = 0;
.global .u32 y = 0;

A1: ld.global.u32 %r0, [x];
B1: st.global.u32 [y], 1;
 
A2: ld.global.u32 %r1, [y];
B2: st.global.u32 [x], 1;
最终状态（FINAL STATE）：x == 1 且 y == 1

该 litmus test 与前者的区别在于它无条件地向 x 与 y 存储 1。在此 litmus test 中，最终状态 x == 1 且 y == 1 是允许的。该执行并不与前一 litmus test 所展示的要求矛盾。这里不存在自我满足的环——它总会、且无条件地向 x 与 y 存储 1，因此该环并非自我满足，投机是有效的。

此处缺乏依赖是明显的，但实现可能进行任意推理链以确定某次存储不依赖于先前的加载，从而打破原本会被 No-Thin-Air 公理禁止的自我满足环。这种形式的加载缓冲在 PTX 内存一致性模型中被刻意允许。

8.10.5　每位置顺序一致（Sequential Consistency Per Location）

在任意"两两道德强的重叠内存操作"集合中，通信序不得与程序序矛盾——即，重叠操作之间的程序序与通信序中道德强关系的拼接，不得形成环。这保证了每个"两两道德强的重叠操作"的程序切片（program slice）都严格顺序一致。

Litmus Test：CoRR

Litmus Test: CoRR（Coherent Read-Read）
T1T2
 
.global .u32 x = 0;

W1: st.global.relaxed.sys.u32 [x], 1;
 
R1: ld.global.relaxed.sys.u32 %r0, [x];
R2: ld.global.relaxed.sys.u32 %r1, [x];
若 %r0 == 1 则 %r1 == 1

litmus test "CoRR"（Coherent Read-Read，相干读-读）展示了该保证的一个推论。线程 T1 在位置 x 上执行一次写 W1，线程 T2 在同一位置 x 上执行两次（或无限序列）读 R1 与 R2。除建模初值的那次写外，x 上不执行其他写。操作 W1、R1、R2 两两道德强。若 R1 读取自 W1，则随后的读 R2 也必须观察到相同的值。若 R2 反而观察到了 x 的初值，则会形成通信序上 R2→W1→R1 的道德强关系序列，与线程 T2 中的程序序 R1→R2 矛盾。因此在此类执行中 R2 不能读取 x 的初值。

8.10.6　因果性（Causality）

通信序中的关系不得与因果序矛盾。这约束了读操作可从中读取值的候选写操作集合：

  • 若读 R 在因果序上先于重叠的写 W，则 R 不能读取自 W。
  • 若写 W 在因果序上先于重叠的读 R，则对于 R 与 W 共同访问的任意字节，R 不能读取自任何"在相干序上先于 W 的写 W′"。

Litmus Test：消息传递（Message Passing）

Litmus Test: MP（Message Passing）
T1T2
 
.global .u32 data = 0;
.global .u32 flag = 0;

W1: st.global.u32 [data], 1;
F1: fence.sys;
W2: st.global.relaxed.sys.u32 [flag], 1;
 
R1: ld.global.relaxed.sys.u32 %r0, [flag];
F2: fence.sys;
R2: ld.global.u32 %r1, [data];
若 %r0 == 1 则 %r1 == 1

名为"MP"（消息传递）的 litmus test，代表了典型同步算法的精髓。绝大多数有用的程序都可归约为该模式的有序应用。

线程 T1 先写数据变量，再写标志变量；而线程 T2 先读标志变量，再读数据变量。对标志的操作道德强，且每个线程内的内存操作被一道屏障隔开，这些屏障也是道德强的。

若 R1 观察到 W2，则释放模式"F1; W2"与获取模式"R1; F2"同步。这建立了因果序 W1 → F1 → W2 → R1 → F2 → R2。于是公理 causality 保证 R2 不能读取自任何"在相干序上先于 W1"的写。在本例无其他写的情况下，R2 必须读取自 W1。

Litmus Test：CoWR

Litmus Test: CoWR（虚拟别名需别名代理屏障）
T1预期
 
// 这些地址是别名
.global .u32 data_alias_1;
.global .u32 data_alias_2;

W1: st.global.u32 [data_alias_1], 1;
F1: fence.proxy.alias;
R1: ld.global.u32 %r1, [data_alias_2];
 
%r1 == 1

虚拟别名（virtual alias）在同步路径上需要一个别名代理屏障（alias proxy fence）。

Litmus Test：存储缓冲（Store Buffering）

名为"SB"（存储缓冲）的 litmus test，展示了 fence.sc 强制的顺序一致性。线程 T1 先写第一个变量再读第二个变量，而线程 T2 先写第二个变量再读第一个变量。每个线程内的内存操作被 fence.sc 指令隔开，且这些屏障道德强。

Litmus Test: SB（Store Buffering）
T1T2
 
.global .u32 x = 0;
.global .u32 y = 0;

W1: st.global.u32 [x], 1;
F1: fence.sc.sys;
R1: ld.global.u32 %r0, [y];
 
W2: st.global.u32 [y], 1;
F2: fence.sc.sys;
R2: ld.global.u32 %r1, [x];
%r0 == 1 或 %r1 == 1

在任何执行中，要么 F1 在 Fence-SC 序上先于 F2，要么反之。若 F1 在 Fence-SC 序上先于 F2，则 F1 与 F2 同步。这建立了因果序 W1 → F1 → F2 → R2。公理 causality 确保 R2 不能读取自任何"在相干序上先于 W1"的写。在本例该变量无其他写的情况下，R2 必须读取自 W1。类似地，当 F2 在 Fence-SC 序上先于 F1 时，R1 必须读取自 W2。若本例中每个 fence.sc 被 fence.acq_rel 指令替换，则该结果不保证。可能存在这样一种执行：每个线程的写都未被另一线程观察到，即可能两个 R1 与 R2 分别对变量 y 与 x 返回初值 "0"。

8.11　特殊情况（Special Cases）

8.11.1　归约不形成获取模式（Reductions do not form Acquire Patterns）

像 red 这样的原子归约操作，不会与获取屏障形成获取模式。

Litmus Test：带 Red 指令的消息传递（Message Passing with a Red Instruction）

Litmus Test: MP with red
T1T2
 
.global .u32 x = 0;
.global .u32 flag = 0;

W1: st.u32 [x], 42;
W2: st.release.gpu.u32 [flag], 1;
 
RMW1: red.sys.global.add.u32 [flag], 1;
F2: fence.acquire.gpu;
R2: ld.weak.u32 %r1, [x];
%r1 == 0 且 flag == 2

名为"MP"的 litmus test 展示了"归约被排除在获取模式之外"的后果。有可能观察到这样的结果：R2 从 x 读取值 0，且 flag 的最终值为 2。该结果是可能的，因为 T1 中的释放模式不与 T2 中的任何获取模式同步。改用 atom 指令而非 red 可禁止该结果。
